# Brief — 메일 목록 새로고침 (버튼 · F5 · 당겨서 갱신)

> **범위**: GUI 만. 사용자가 직접 목록을 다시 읽게 하고, 로딩 표시 위치를 정리한다. 코어·Tauri 명령은 바꾸지 않는다 —
> 새로고침은 이미 있는 `mail_sync`(변경분 동기화, 실시간 갱신과 같은 경로)다. 규칙은 [gui/AGENTS.md](../gui/AGENTS.md),
> 실시간 갱신은 [DESIGN-MAIL-GUI.md](DESIGN-MAIL-GUI.md) "실시간 갱신".

2026-11-24 작성. "소유자 결정" 은 확정, 나머지는 착수 지시다. 측정이 지시와 어긋나면 멈추고 보고한다.

## 왜 필요한가

푸시가 오면 목록은 이미 저절로 바뀐다. 하지만 **Stalwart 1.1.0 은 공유받은 Account 의 변경을 푸시하지 않는다**
(2026-11-24 창 실측). 그 화면에서는 새로고침이 유일한 갱신 수단이다. 푸시를 광고하지 않는 서버도 같다.

## 소유자 결정

```txt
진입      목록 머리의 새로고침 버튼(선택 모드 버튼 옆) · F5 · 당겨서 갱신(터치, 목록 맨 위에서만).  버튼은 항상 둔다 —
          제스처가 유일한 방법이 되지 않게 (M3 gestures)
표시 위치  "보여 줄 목록이 이미 있느냐" 로 정한다:
            첫 로드(행 없음)          목록 영역 중앙
            새로고침(버튼·F5·당김)    셋 다 목록 상단 가운데 같은 자리, 행 위에 떠서 — 목록을 밀지 않는다
            백그라운드 푸시            표시 없음
배너      "새 메시지 N개" 는 이번에 없다
```

## 지금 상태 — 읽고 시작

- `mail-page.component.html` 은 `view.isLoading()` 이면 목록 위에 `<p class="status">Loading…</p>` 를 넣는다. 이건 첫 로드와
  `view.reload()`(쓰기 뒤·푸시 뒤) 를 가리지 않아서, 푸시마다 한 줄이 끼었다 빠지며 목록을 민다. 이번에 바로잡는다:
  **행이 없을 때만** 중앙 표시, 행이 있으면 그 줄을 넣지 않는다.
- 푸시·쓰기 뒤 갱신은 `MailActions.changed` → `view.reload()`. 새로고침도 같은 reload 를 쓰되, **사용자가 시작한 것만**
  상단 표시를 띄운다 — 표시 여부는 `isLoading` 이 아니라 "사용자 새로고침 진행 중" 상태로 정한다.

## 지시

1. **새로고침 동작 하나**: 현재 연결·Account·메일함의 목록을 다시 읽는다(`view.reload()` — 메일함 badge 도 같이).
   진행 중이면 다시 누르거나 F5 를 눌러도 하나로 합친다. 열린 메일·선택·결과 모름 잠금·트리 펼침·포커스·스크롤 위치
   유지(실시간 갱신과 같은 경로라 이미 그렇다 — 깨지지 않았는지 확인). 실패하면 기존 오류 표시 + 알림, 행은 그대로.
2. **표시**: 원형 surface 컨테이너 안 `mat-progress-spinner`(M3 당겨서 갱신의 contained loading indicator 모양 —
   Angular Material 에 M3 Expressive loading indicator 가 없으므로). 목록 상단 가운데, sticky 머리 아래에 떠서. 첫 로드는
   같은 spinner 를 목록 중앙에(컨테이너 없이 가능). **깜빡임 방지**: 300ms 안에 끝나면 띄우지 않고, 띄웠으면 최소
   500ms. 화면 낭독기: `role="status"` 로 "Refreshing…", 끝나면 조용히(성공 알림 없음).
   첫 로드와 새로고침에는 진행률을 알 수 없으므로 `mode="indeterminate"` 스피너를 쓴다. `mat-progress-bar`는 첨부 전송처럼 진행률을 계산할 수 있는 작업에 남겨 둔다.
3. **버튼**: 목록 머리, 선택 모드 버튼 옆, `refresh` 아이콘 + 툴팁 "Refresh". 진행 중엔 비활성. 선택 모드 머리에는 두지 않는다.
4. **F5**: 메일 화면에서 F5·Ctrl+R 을 가로채(`preventDefault`) 새로고침 동작으로. Tauri 웹뷰 기본은 페이지 전체 재시작이라
   열린 메일·선택·잠금이 다 사라진다. 입력란에 포커스가 있어도 같다. 개발용 전체 재시작이 필요하면 Ctrl+Shift+R 을 남길지
   판단해 보고(남기면 개발 빌드에서만).
5. **당겨서 갱신**: 터치 입력(`pointerType === "touch"`)이고 목록이 맨 위(`scrollTop === 0`)일 때만. 당기는 거리만큼 표시가
   내려오고, 임계(예: 64px)를 넘겨 놓으면 새로고침, 못 넘기면 되돌아간다. 마우스 드래그로는 동작하지 않는다.
   `overscroll-behavior` 로 웹뷰 기본 바운스와 겹치지 않게. 데스크톱에서는 창 검증이 어려우니 상태 계산(거리→단계)을
   순수 함수로 빼서 spec 으로 고정한다.

## 하지 않는 것

"새 메시지 N개" 배너(나중 — 사용자가 아래를 읽는 동안 새 행이 위에 들어올 때를 위해; 크로미움 scroll anchoring 이 보던
행을 붙잡는지 먼저 실측), 푸시 성공·실패 표시, 자동 주기 갱신, 코어·Tauri 변경.

## 검증

```txt
node --test "gui/src/**/*.spec.ts"   당김 거리→단계, 표시 지연·최소 시간, 진행 중 합치기
npm --prefix gui run build
```

창에서(원격 디버깅 CDP — DESIGN-MAIL-GUI.md "메일함 트리" 의 측정 경로, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=
--remote-debugging-port=9222`): 공유 Account 화면에서 외부 생성 → 푸시 없음 → 버튼·F5 로 반영. F5 뒤 열린 메일·선택이
남아 있는지(페이지가 다시 시작되지 않았는지 — `performance.timeOrigin` 이 그대로인지로). 푸시 갱신 때 목록이 밀리지 않는지
(첫 행의 `getBoundingClientRect().top` 이 갱신 전후 같은지). 첫 로드 중앙 표시, 새로고침 상단 표시 스크린샷. 당겨서 갱신은
CDP `Input.dispatchTouchEvent` 로 시도하고, 안 되면 못 본 것으로 보고.

끝나면 바꾼 파일, 본 것, 못 본 것을 보고. 커밋은 사용자 승인 뒤.
