# Brief — 원격 Object 를 **어느 Actor 의 권한으로** 가져올 것인가

> **범위**: 홈 서버가 선택된 Actor 의 키로 원격 Object 를 서명 GET 하는 경로. 그 권한 판정과
> 캐시 계약까지. GUI 와 익명 열람은 이 슬라이스가 아니다.
> 이웃: [C2S.md](C2S.md) · AP Session(`includes/c2s-session.php`) ·
> OP 의 원격 캐시(`axismundi-object-projections/includes/remote-objects.php`)

## 구현 순서

1. **로컬 인증 읽기.** OP에서 로컬 Actor 문서와 로컬 Object의 읽기 판정을 검증한다.
   WordPress 인증 주체와 요청에 명시된 viewer Actor를 따로 확인하며, 브라우저가 선택한
   acting Actor를 대신 쓰지 않는다. Actor 자기 문서 접근과 Object의 audience 판정도
   별개다. 공개 GET과 기존 URL은 그대로 두고, 이 단계에서 resolve 경로나 원격 호출을
   추가하지 않는다.
2. **로컬 resolve.** URI, 사람용 URL, WebFinger 식별자(`acct:` 또는 핸들)를 한 동작으로
   받는다. 식별자 해석 실패와 문서 조회 실패를 구분한다. 로컬의 기존 URI/별칭/핸들만
   해석하고, 원격 WebFinger나 GET은 이 단계에서 실행하지 않는다. 클라이언트는 세션의
   Actor URI로 자기 문서를 조회하고, 세션에 전체 Actor 문서를 중복해서 싣지 않는다.
3. **원격 resolve.** OP가 읽기 동작을 소유하고 브리지가 서명 GET 전송을 맡는다. OP는
   개인키를 읽지 않는다. 응답 문서의 타입으로 분기하고 기존 Actor/Object 저장소의
   소유권을 유지한다. 컬렉션(outbox, sharedInbox 등)과 조회만 한 Activity는 읽기 전용
   결과로 반환하며, 별도 캐시나 원장 행을 만들지 않는다. GET으로 본 Activity는 배달이
   아니며 Inbox 처리기나 활동 부작용을 실행하지 않는다. 원격이 컬렉션 GET을
   거부하거나 지원하지 않는 것은 정상 조회 결과다.

**첫 단계의 감사:** 공개 조건을 통과하지 않은 Actor의 자기 문서는 권한 있는 사용자만
읽을 수 있어야 한다. 이 사실이 AP Session에 outbox 제출 주소를 추가할 근거는 아니다.
그 세션은 기존 제출 권한을 계속 광고한다. 같은 audience로 발행한 제한 공개
`Create`와 Object 조합은 A(저자)·B(허용된 팔로워)에게 둘 다 보이고 C(무관)에게
둘 다 보이지 않아야 한다. 이 단정은 같은 audience의 픽스처에 한정한다. 수신된 모든
Activity의 가시성이 현재 Object의 가시성과 항상 같다는 계약은 아니다. 브라우저 선택
없이 B가 읽히는지, B를 대신할 권한이 없는 로그인은 B를 명시해도 거부되는지도 따로 잰다.

로컬 구현의 인증 읽기는 `GET /wp-json/axismundi/activitypub/actors?ids={actorUris}`와
`GET /wp-json/axismundi/activitypub/objects?ids={objectUris}&actor={viewerUri}`를 사용한다.
`ids`는 쉼표로 구분한 정규 URI 목록이다(최대 20개, 디코딩된 값 6000바이트 이하).
한 건이어도 `OrderedCollection`의 `orderedItems`로 반환하고, 없거나 권한이 없는 항목은
구분 없이 생략한다. 전자는 Workspace 권한으로 자기 Actor 문서를 읽고,
후자는 명시한 Actor의 열람 권한으로 로컬 Object를 읽는다. URI를 숫자 ID로 바꾸는 작업은
클라이언트에 맡기지 않는다. 기존 숫자 ID 경로와 정규 공개 URI는 유지하며 새 GET은 원격
요청을 하지 않는다. `axismundi/activitystreams`의 미발행 객체 GET/PATCH 및 타입 발견은
별도 계약으로 남는다.

읽기 허가와 별개로, 인증된 Actor에게는 해당 문서의 최상위 `bto`·`bcc`를 보여줄 수 있다.
Object는 자기 `attributedTo`, Activity는 자기 `actor`의 모든 URI와 비교한다. Object에
대응하는 Create를 원장에서 조회하거나, 중첩 Object의 저작을 바깥 Activity에 적용하지 않는다.
중첩 문서·익명 조회·연합 배달에는 이 예외를 적용하지 않는다. 복수 값 판정은 쓰기 모델을
확장하거나 기존 본문 열람 권한을 넓히지 않는다.

**원격 단계의 범위:** [ActivityPub B.5](https://www.w3.org/TR/activitypub/#security-recursive-objects)에
따라 컬렉션 항목이나 페이지 링크를 자동으로 따라가지 않는다.
[B.9](https://www.w3.org/TR/activitypub/#security-c2s-response-dos)에 따라 반환할 페이지
크기를 제한하되, 너무 큰 원격 페이지를 조용히 잘라 완전한 페이지처럼 내주지 않는다.
기존 URL 검증, 리다이렉트 검증, 응답 바이트 한도는 유지한다. 사용자·Actor별
**조회 횟수 제한**과 그 광고 형식은 보류한다.
[B.8](https://www.w3.org/TR/activitypub/#security-c2s-ratelimiting)의 제출 제한을
조회 횟수 제한의 근거로 쓰지 않는다.

## 메우려는 공백

ActivityPub 에 **"이 원격 URI 를 대신 조회해 달라"는 C2S 메서드가 없다.**

```txt
있다   §3.2 — Object 의 id 자체를 AS2 Accept 로 GET 한다.  원본 서버가 인증·접근제어를 걸 수 있다
       §7 도 같은 규칙을 쓴다 — Actor URI 를 GET 해 inbox 주소를 읽고 거기 POST 한다
없다   홈 서버에 "이 URI 의 캐시를 줘 / 없으면 가져와 줘 / 내 Actor 로 원본을 다시 읽어 줘"
       inbox·outbox 계약에 그 자리가 없다
우리    /axismundi/v1/objects/{id} 는 **내부 숫자 id** 로 읽는 애플리케이션 API 다.
       임의의 원격 URI 를 해결하는 경로가 아니다
```

AP Session 이 메우는 것은 **"누구로 요청할 수 있나"** 이고, 이 슬라이스가 메우는 것은
**"그 권한으로 홈 서버에 무엇을 가져와 달라고 할 수 있나"** 다. 연결되지만 같은 기능이 아니다.

## 가장 중요한 한 줄

**배달 서명은 역방향 조회 자격증명이 아니다.**

inbox POST 의 서명은 **발신자가 보낸 요청**을 검증한다. 그 POST 를 받았다는 사실이 수신자
Actor 의 권한으로 원본에 나가도 된다는 **위임이 아니다.** 그 위임은 지금 어디에도 없다.

```txt
따라서   **Inbox 수신만으로는 서명 GET 을 하지 않는다.**  이것이 계약이다
근거     "언제 가져올지의 정책" 이 아니라 **"누구의 권한으로 가져오는가"** 에 답이 없기 때문이다
위임의 출처  인증된 클라이언트가 **Actor 를 명시해** 열람을 요청하는 것.  그것이 신호다
```

## 수신 시점에 하는 일

```txt
본문이 실려 왔다      검증한 뒤 저장한다.  원본 GET 0회.
                   읽을 때 **요청 Actor 에게 내줘도 되는지는 따로 판정**한다
URI 만 왔다          Activity 와 URI 만 저장한다.  가져오지 않는다
```

URI 만 온 상태를 캐시 테이블에 미리 예약하지 **않는다.** 측정: 원격 캐시 스키마가
`payload_json longtext NOT NULL`, `payload_hash char(64) NOT NULL` 이라 미조회 자리를 만들려면
가짜 `{}` 를 넣어야 한다. **첫 구현은 원장의 `object_uri` 자체를 미조회 참조로 쓴다.** 캐시
행은 본문을 실제로 받았을 때만 만든다. 자리를 예약할 이유가 생기면 그때 **`미조회` 와
`본문 있음` 을 명시적으로 구분**한다 — 둘을 같은 행으로 뭉개지 않는다.

## 열람 흐름

```txt
① 클라이언트 → 홈 서버   선택한 Actor URI + 조회할 Object URI
② 홈 서버              그 사용자에게 can_act_as(Actor) 가 있는지 확인
③ 홈 서버 → 원본        **그 Actor 의 키로 새 GET 을 서명**한다
④ 원본                팔로우·멘션 등 접근 조건을 **원본이** 판단한다
⑤ 홈 서버 → 클라이언트   원본의 성공·거부를 보존하고, 성공한 문서만 읽기용으로 투영한다
```

```txt
금지   클라이언트의 인증 헤더나 서명을 원격에 **그대로 전달**하는 것.  새로 서명한다
금지   개인키를 데스크톱에 주는 것.  키는 홈 서버에 남는다
금지   **임의 URL 에 Actor 서명을 붙여 주는 범용 프록시.**  이름 붙은 동작만 연다
금지   AP Session 에 Actor 가 보인다는 이유로 서명 조회 권한을 주는 것.
       지금 Session 은 **outbox 제출 가능 여부**를 말한다.  서명 조회는 별도 동작이다
```

## 캐시 — 본문 보유와 열람 허가는 다르다

[OP의 원격 객체 계약](../../axismundi-object-projections/docs/REMOTE-OBJECTS.md#6-cache-levels-and-binary-boundary)에
캐시 범위를 둔다. 서명 GET은 같은 문서에서 이미 예고한 Federation fetch capability를
브리지가 제공하는 일이다. **사용자가 명시적으로 요청한 resolve만** 원격으로 나가며, 기존
렌더 경로에서 캐시 미스로 네트워크에 동기 접근하지 않는 규칙은 그대로다.

읽기용 투영은 원본 및 저장본의 `id`, 저자, 주소 지정과 알 수 없는 확장 속성을 보존한다.
로컬 문서는 기존 렌더 결과를 쓰고 resolve에서 다시 표백하거나 미디어를 치환하지 않는다.
원격 문서에서는 표시용 HTML을 정화하되 어휘를 잘라내지 않는다. URL 치환은 **원격 Actor의
아바타·헤더**에 한해, 공개로 제공해도 되는 기존 캐시본이 있을 때만 응답에 적용한다.
원격 Object의 Image나 첨부에는 바이너리 사본이 없으므로 URL을 바꾸지 않는다. 나머지
외부 미디어를 불러올지는 클라이언트의 사용자 옵션이 결정한다. 이 투영은 원본의 거부를
성공으로 바꾸거나 다른 Actor에게 열람 권한을 주지 않는다.

```txt
본문은 URI 당 한 벌로 저장해도 된다
공유하면 안 되는 것은 **"이 본문을 읽어도 된다" 는 판정**이다
A 의 서명 GET 이 받은 200 은 **A 에 대한 결과**다.  B 나 같은 WordPress 로그인 전체에 대한
허가가 아니다
```

```txt
유효한 캐시가 있다       그 Actor 가 읽을 수 있으면 원본에 다시 요청하지 않는다
만료                  다음 열람 때 재조회한다
검증된 Update 수신      본문이 실려 있으면 GET 없이 갱신할 수 있다.
                     URI 만 오면 다음 열람 때 재조회한다
                     **본문 갱신만으로 열람 대상을 넓히지 않는다**
원본이 거부            **이전 본문을 대신 내주지 않는다.**  거부를 거부로 돌려준다
```

마지막 줄이 이 슬라이스에서 가장 틀리기 쉬운 자리다. 캐시를 대신 보여주면서 원본 조회
성공으로 처리하면, 사용자는 지금 읽을 권한이 있다고 믿게 된다.

## 감사 — 캐시가 **찬 뒤**가 본론이다

같은 URI 에 대해 `A`(팔로워 또는 실제 수신 대상)와 `B`(권한 없음)를 두고, **둘을 같은
WordPress 사용자가 운영**하게 한다. 그래야 Account 와 Actor 를 혼동하는 버그까지 잡힌다.

```txt
① URI 만 있는 Create 수신        원본 GET **0회**
② A 로 처음 열기                 **A 의 서명으로 GET 1회**, 본문 반환
③ A 로 다시 열기                 **추가 GET 없이** 캐시 반환
④ B 로 같은 URI 열기             **캐시가 있어도 본문을 받지 못한다**
⑤ 만료 후 원본이 A 를 거부        **이전 본문을 대신 내주지 않는다**
```

```txt
세는 것   원본 GET **횟수**를 센다.  "되더라" 가 아니라 몇 번 나갔는지가 ①③의 전부다
변이     can_act_as 검사를 지우면 별도 로그인이 A를 명시한 요청의 거부 단정이 실패해야 한다.
        캐시 반환 조건에서 Actor 판정을 빼면 ④가 실패해야 한다.
        거부 시 캐시 폴백을 넣으면 ⑤가 실패해야 한다
```

**④가 핵심이다.** 그 자리가 비면 "URI 당 본문 한 벌" 이 곧 "누구나 읽어도 된다" 가 된다.

## 발행 측 불변식 — 주소를 Object 에서 가져온다

조회 정책의 입력이 흔들리지 않게, 우리가 발행하는 활동의 주소를 Object 에 맞춘다.

```txt
Create   발행 직전 저장된 Object 의 주소를 Create 에 반영한다.
         §6.2.1 도 단독 Object 를 감쌀 때 주소 속성을 **Object → 활동** 방향으로 복사하게 한다.
         참조형 Create 에서는 **반대 방향으로 Object 를 고치지 않는다** (FEP-c3ab 규칙 1)
Update   주소를 바꾸지 않는 편집이면 기존 Object 의 주소를 쓴다.
         가시성 변경은 별도 정책이다 — 대상을 줄였다고 **이전 수신자의 캐시가 회수되지 않는다**
```

```txt
금지   원격에서 받은 활동과 Object 의 주소가 다르다고 둘을 합쳐 공개 범위를 넓히는 것
금지   수신 사실만으로 GET 권한을 추정하는 것
위치    주소는 배달과 조회 정책의 **입력**이지, 서명 GET 의 위임도 캐시 열람 허가도 아니다
```

## 없는 것 — 먼저 만들어야 한다

```txt
서명 GET 엔드포인트   **없다.**  AP Session 은 Actor 발견까지다.
                   Mastodon 이 그런 요청을 존중한다는 것은 소스로 확인했고
                   (signature_authentication.rb · status_policy.rb),
                   **우리 쪽 엔드포인트는 구현되지 않았다**
상호운용 전제        원본이 서명 GET 으로 제한 공개를 내준다는 것은 **Mastodon 의 규칙**이다.
                   모든 구현이 같다고 가정하지 않는다.  거부도 정상 결과다
```

## 바꾸지 말 것

```txt
키의 위치      개인키는 홈 서버에 남는다
IPC·API 표면   이름 붙은 동작만.  URL·헤더를 받는 범용 요청을 열지 않는다
세 결과 구분   익명 원본 / 내 Actor·캐시 / 내 Actor·원본 재조회.
             재조회가 거부됐을 때 캐시를 슬쩍 대신 보여주며 성공이라 하지 않는다
```
