# Geodata 확장 방향

상태: 설계 논의 정리. 현재 구현이나 표준 준수 목록이 아니다.
Outbox가 먼저이며, Geodata의 첫 구현 범위는
[공간 Feature 실험](spatial-feature-experiment.md)에서 따로 정한다.

## 목표: 지리정보 발행의 민주화

누구나 자기 서버에서 지리정보를 등록·수정·발행하고, 다른 서버나 GIS가
특정 플랫폼의 허락 없이 읽고 연결할 수 있게 한다. 지도는 소비 화면 중
하나다. Google Places는 선택적 검색·참조 제공자이며, 연결을 끊어도 자체
Place URI와 자체 발행 데이터는 살아 있어야 한다.

기존 `geo_area`·`geotag`는 WordPress 콘텐츠의 공간 분류다. 독립 Place는
게시물 없이도 존재하는 구조화된 메타데이터 객체다. Geodata 커스텀 저장소를
추가하되 기존 term, 게시물 좌표, 공개 경로는 자동으로 옮기지 않는다.
장소 소개문이 필요하면 Page나 Article에서 참조할 수 있다. Place CPT는
블록 편집이 필요한 별도 요구가 생길 때만 검토한다.

## 객체, 형상, 권위

- **객체와 형상:** Place는 공간 Feature로 제공할 수 있지만 모든 Feature가
  Place는 아니다. 경로, 행정 경계, 건물 외곽, 측정 지점도 공간 조회의
  대상이다. 대표점, 실제 경계, 출입구, 지도 표시 범위는 역할이 다르다.
- **공간과 운영:** 같은 건물에 여러 업체가 있거나 운영자가 바뀔 수 있다.
  장소, 업체, 운영 기간을 구분한다. 운영시간과 예외일, 휴업, 주차,
  접근성, 반려동물 동반 조건은 구조화할 후보다. 메뉴·예약·리뷰·이벤트는
  필요에 따라 별도 객체가 Place 또는 업체를 참조한다.
- **출처와 공개:** 자체 작성, 운영자 제공, 외부 관측을 구분한다. 변경되는
  속성은 필요하면 필드별 출처·확인일·조건을 남긴다. 제공자 ID를 연결하는
  것과 응답 데이터를 저장·재배포하는 것은 별개다. Google·OSM 등은 각
  데이터 이용 조건을 별도로 확인한다. 개인 카드 주소나 EXIF 좌표가 지도에
  표시된다고 공개 컬렉션에 들어가서는 안 된다.
- **귀속과 권한:** AS2 `attributedTo`는 Place 레코드의 발행 귀속이다.
  실제 장소의 소유·운영권이나 다른 객체의 수정 권한을 부여하지 않는다.
  리뷰 원본은 작성자가 관리하고, 장소 서버가 할 수 있는 것은 자기 목록에서
  제외하는 것까지다.

## 읽기 표면과 연동 후보

| 표면 | 도입 방향 |
| --- | --- |
| OGC API – Features | Core의 컬렉션 발견·아이템 조회·bbox·페이지네이션부터. 필요할 때 Part 3/CQL2, Part 5/Schemas, 추가 CRS 검토 |
| GeoJSON / JSON-FG | GeoJSON 기본. JSON-FG는 CRS·유효 시간·형상·유형 표현이 실제로 필요할 때 추가 |
| MySQL / MariaDB Spatial | Geometry 저장, 인덱스 후보 검색과 정확 교차 판정. SQL과 DDL 이식성은 실험에서 확인 |
| Map / `/maps/` | 기존 Map 렌더링 자산 재사용 검토. 배경 지도·PMTiles와 OGC Feature 오버레이 분리. 뷰포트 검색, 목록·상세, 경로 표시 후보 |
| Contacts / Calendar | 주소·장소 선택과 미리보기는 Geodata를 선택적으로 사용. 개인 카드 주소와 Event 원본은 각 도메인 소유 |
| AS2 / GeoRSS | AS2 Place와 게시물·이벤트의 `location` 연결. GeoRSS는 피드 항목의 위치 표현으로 유지 |
| SKOS / GeoSPARQL | SKOS는 유형 어휘와 외부 매핑 후보. GeoSPARQL RDF 투영과 SPARQL 질의 서비스는 별도 결정 |

하나의 발행 Place URI에서 콘텐츠 협상으로 GeoJSON, JSContact Location
Card, AS2 Place를 제공하는 방향이다. 각 형식의 ID 규칙과 가시성을 검증한
뒤 공통 URI를 투영한다. 표현별 캐시 분리와 쓰기 권한은 별도 계약이다.
OGC 컬렉션은 AddressBook이나 AS2 Collection처럼 객체와 별개로 주소를
가질 수 있지만, 모든 컬렉션을 저장형 멤버십으로 만들 필요는 없다.
`/feed/as2/`와 공유하는 건 pull 기반 읽기·탐색이라는 관점이다.
JMAP은 Contacts·Calendar 동기화에 남기고, 공간 조회의 전제로 두지 않는다.

## 분산 검색과 리뷰

같은 공원을 여러 서버가 독립적으로 등록할 수 있다. 각 URI와 출처를
보존한다. OSM 유형과 ID, Wikidata QID, 좌표 오차, 다국어 명칭과 주소,
유형 및 경계는 매칭 근거다. 일치도·관련도·거리·최신성은 검색 순위일
뿐 동일성 증명이 아니다. 후보를 묶어 보여주는 것과 리뷰·평점 합산은
다른 수준의 근거를 요구한다. 초기에는 후보 표시를 우선하고 원본 병합,
리뷰 대상 변경, 평점 합산은 하지 않는다.

리뷰 대상 Place URI와 개별 리뷰 URI를 보존한다. 공통 장소 식별자는
해시태그처럼 **발견한** 리뷰를 모으는 로컬 인덱스 키가 될 수 있지만
원격 리뷰를 자동으로 가져오지는 않는다. 수신·선택적 pull·구독은 별도
발견 정책이다. Place는 Actor가 아니므로 Place 참조만으로 inbox 배송을
가정하지 않는다. 전역 동기화나 전체 건수도 약속하지 않는다.

## 보류할 결정

- Place 유형 어휘는 기존 Google 기반 term 어휘와 구분한다. OSM·Schema.org
  등과의 매핑, 유형과 편의시설 속성의 분리는 검토하되 SKOS 도입은 필수가 아니다.
- 별도 Place 관리 UI, 필드 권한, 수정 이력, 원격 캐시, 리뷰 발견과 연합,
  공급자 데이터 재사용 정책은 첫 공간 감사 범위 밖이다.
- 반복 지도 조회는 범위·페이지 크기를 제한하고, 공개 표현은 캐시와
  조건부 요청을 검토한다. 원격 서버 전체를 매번 조회하거나 복제하지 않는다.
