# BRIEF — JMAP Mail 범위

이 문서는 **골격과 후속 구현 범위를 정리한다.** 비활성 골격은 지금 만들 수
있고(§0), 모듈의 내용은 조사 뒤에 정한다(§5). 코드는 아직 없다.

## 0. 우리에게 mailstore 가 없다

```txt
wp_mail()        발신 전용. 보내고 끝이며 보낸 것을 보관하지 않는다
수신             없다. IMAP 도 POP3 도 MX 도 우리 것이 아니다
```

RFC 8621 의 `Mailbox` 와 `Email` 은 저장소를 전제한다. `EmailSubmission` 은
**기존 `Email` 을 참조해서** 제출한다 — 이것은 참조이지 "Sent 사본을 보관할
의무" 와 같은 말이 아니다. 둘을 같은 것으로 단정하지 않는다.

그러므로 "JMAP Mail 을 붙인다" 는 말이 무엇인지부터 좁힌다.

```txt
A  발신 표면만        wp_mail 을 JMAP 어휘로 감싼다. Mailbox·Email 저장 없음
B  외부 저장소 연동   WordPress.com 메일박스나 다른 제공자를 뒤에 둔다
C  우리가 저장소      Email 을 우리가 보관한다
D  코어 메일 관찰 투영  사이트가 보낸 메일을 인스턴스 Account 쪽에 기록·투영한다
```

두 가지를 바로잡아 둔다.

```txt
배타적이지 않다   B 와 C 는 양자택일이 아니다. 일부는 외부, 일부는 로컬일 수 있다.
                  D 는 A·B·C 와 독립해서 성립한다 — 앞서 SYSTEM-ACTOR 에 기록한
                  코어 메일 관찰이 그것이고, 저장소 선택을 기다리지 않는다

적합성은 남는다   외부 저장소를 쓴다고 해서 **우리가 내보내는 JMAP 응답의 적합성
                  책임이 사라지지 않는다.** 우리가 Session 과 메서드 응답을
                  제공한다면 그 응답이 RFC 8621 에 맞는지는 우리 책임이다.
                  "프록시라서 제공자 책임" 이 아니다
```

### 뼈대는 지금 만들어도 된다

저장소를 고르기 전에도 **비활성 플러그인 골격과 설계 문서**는 만들 수 있다.
조건은 둘뿐이다.

```txt
메일 capability 를 Session 에 광고하지 않는다
wp_mail 전송을 가로채지 않는다
```

이 둘만 지키면 골격은 아무 동작도 바꾸지 않는다. 저장소 결정을 기다릴 이유가
없다. 결정이 필요한 것은 **모듈의 내용**이지 모듈의 존재가 아니다.

## 1. Account 와 메일 아이덴티티의 단위

우리 JMAP Account 는 **Actor 단위**다 (`ax_jmap_accounts`, 로컬 액터 1:1).
그러므로 자연스러운 배치는 이렇다.

```txt
WP user        한 사람. 여러 Account 를 운영할 수 있다
Account        = 로컬 Actor.  JMAP Session 의 accounts 맵 항목
Identity       RFC 8621 의 발신 주소.  Account 당 0..N
```

정할 것:

```txt
user 당 Account 수 제한        표준에 없다 (RFC 8620 에 해당 필드·규칙 없음).
                               서버 정책이고, 우리 경우 Add Local Actor 지점이다.
                               지금 제한 없음. 둘 이유가 생기기 전에는 두지 않는다
Account 당 메일박스 수 제한    같은 성격. B 를 고르면 제공자 제한이 상한이 된다
Identity 가 Account 에 묶이나  묶는 게 맞아 보인다. 메일 발신 주체와
                               ActivityPub 발신 주체가 같은 Account 라야
                               "이 계정으로 보낸다" 가 한 가지 뜻이 된다
```

## 2. 역방향 유도 — 인스턴스 Actor 의 이름

보통 방향은 **Actor → 메일**이다. 로컬 Actor 의 `preferredUsername` 에서
기본 메일 아이덴티티를 만든다.

인스턴스 Actor 만 **거꾸로** 되어 있다.

```txt
워드프레스 코어   기본 발신자가 wordpress@<도메인>
그래서            system-actor.php:37
                  get_option( 'ax_actors_system_actor_username', 'wordpress' )
                  인스턴스 Actor 의 preferredUsername 을 'wordpress' 로 잡았다
```

즉 **코어 메일 주소가 Actor 이름을 정했다.** 편의상 그렇게 둔 것이고 임시다.
메일을 붙일 때 이 방향을 그대로 둘지 뒤집을지 정해야 한다.

```txt
유지   코어 메일과 인스턴스 Actor 가 한 이름을 공유한다. 운영자에게 직관적이다
       대신 Actor 이름이 메일 관례(wordpress@)에 묶인다
뒤집기 Actor 이름을 먼저 정하고 코어 발신 주소를 거기에 맞춘다
       wp_mail 의 from 을 필터로 바꾸면 된다. 다만 기존 사이트의 발신 주소가
       바뀌는 변경이라 조용히 하면 안 된다
```

어느 쪽이든 **핸들은 한 번 정하면 영구에 가깝다** (DATA-MODEL 의 핸들 정책).
그러므로 메일 설계가 인스턴스 Actor 의 이름을 바꾸길 원한다면, 그 결정은
메일보다 먼저이고 Actors 쪽 결정이다.

## 3. 코어 메일과의 연동 — 프로토콜을 제공하되 다른 경로를 막지 않는다

**JMAP Mail 표준 표면을 구현하는 것과, 모든 메일을 그 경로로 강제하는 것은
별개다.** 전자는 하고 후자는 하지 않는다.

```txt
자동화 메일      비밀번호 재설정 · 알림 · 가입 확인
                 mailbox 에 보관하려는 의도가 아니라 전달하려는 의도다.
                 기존 코어·전용 전송 경로를 그대로 유지해도 된다
사람의 메일      JMAP 표면을 쓴다
관찰 투영        사이트가 보낸 것을 인스턴스 Account 쪽에 기록·투영하는 일은
                 위 둘과 독립해서 붙일 수 있다 (0 의 D)
```

안전 기준은 그대로다. **코어의 인증·복구 메일 경로를 우리 구현에 의존시키지
않는다.** 우리 플러그인이 꺼져도 사이트는 비밀번호 재설정 메일을 보낼 수 있어야
한다. 이것은 전용 경로를 **막지 않는 이유**이기도 하다.

### 발신 주체는 이미 정해져 있다

코어 전송은 그대로 두고, 인스턴스 Account 에는 **관찰 기록을 투영한다.**
Account 가 발신 주체가 되는 것이 아니다. 이건 미결이 아니라 기록된 결정이다
— `axismundi-actors/docs/SYSTEM-ACTOR.md` 를 보라.

그 결정이 함께 정한 안전 계약도 여기 옮겨 둔다.

```txt
투영 대상    Mailbox(role=sent) 에 Email 만. EmailSubmission 은 두지 않는다
             — 우리가 제출한 것이 아니다
기록 범위    메타데이터만. 수신자 · 제목 · 시각 · 성공/실패 · 발신 Identity
             **본문과 첨부는 적지 않는다**
이유         코어 메일 본문에 비밀번호 재설정 링크가 들어간다. 시스템 Account 는
             부여가 없어 manage_options 로 열리므로, 본문을 적으면 그 발신 기록이
             운영자용 계정 탈취 경로가 된다
```

남는 질문:

```txt
전송 실패·바운스    wp_mail 은 bool 만 돌려준다. 상태를 남기려면 우리가 기록해야
```

## 4. Quota 는 보류

RFC 8620 의 quota 확장은 Account 수가 아니라 저장 용량을 다룬다. 우리는
워드프레스 미디어 렌디션 때문에 **무엇을 세는지부터 정해지지 않았다** —
렌디션마다 셀지, 대표본만 셀지는 호스팅 정책마다 다르다. 메일 저장소(C)를
고르지 않는 한 급하지 않다. TODO-POC 의 ⑤ 와 같은 보류다.

## 5. 다음 행동

```txt
1  비활성 골격 + 이 문서      저장소 결정을 기다리지 않는다.
                              capability 광고 없음, wp_mail 가로채기 없음
2  조사                       WordPress.com 메일박스와 기존 메일 플러그인이
                              외부에 무엇을 여는지
3  조사 결과로 모듈의 내용을 정한다   A·B·C·D 의 조합
```

순서가 이런 이유는, 골격은 아무것도 바꾸지 않지만 **모듈의 내용은 조사 결과에
따라 전혀 달라지기** 때문이다. B 는 인증·토큰 보관이 핵심이고 C 는 저장소와
보존 정책이 핵심이다. 내용을 먼저 쓰면 폐기할 것을 쓰게 된다.
