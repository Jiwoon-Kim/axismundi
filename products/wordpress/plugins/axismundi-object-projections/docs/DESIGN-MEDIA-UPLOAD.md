# 발행용 미디어 업로드

AP C2S 의 `uploadMedia` 를 OP 가 구현한다. 경로·소유·공개 저장 경로는 이미 결정돼 있다 —
`products/wordpress/architecture/activitystreams-open-items.md` 의 `uploadMedia`·`바이트`·
`공개 업로드` 항목. 이 문서는 **그 위에서 와이어 계약을 정한다.**

단계 분해의 근거는 `axismundi-activities/docs/C2S.md` §14 다. 업로드는 **1단계**(바이트와
객체 식별)이고, `Create` 는 2단계다. 업로드가 발행이 아니라는 것은 제품 정책이기도 하고
단계 정의이기도 하다.

## 1. 2017 CG 초안의 결함 (측정)

[SocialCG/ActivityPub/MediaUpload](https://www.w3.org/wiki/SocialCG/ActivityPub/MediaUpload)
은 **2017-10-24 마지막 수정된 W3C 위키 페이지**다. 저자 표기가 없고 규범 선언이 없다.
MUST/SHOULD 표기를 쓰지만 그것이 규범성을 만들지는 않는다. AP §6.12 Uploading Media 가
non-normative 이고 "the precise mechanism is out of scope" 라고 말하는 그 공백에 놓인
커뮤니티 문서다.

계약은 `endpoints.uploadMedia` 에 `multipart/form-data` 로 파트 둘(`file`, `object` 껍데기),
`201` 또는 처리 중이면 `202`, `Location` 은 "the new **or to-be-created** object's `id`",
서버가 `id` 를 붙이고 `url` 에 처리된 파일 경로를 담기를 SHOULD, `Create` 래핑은 MAY.

결함은 다섯이다.

```txt
완료 신호가 없다       예시는 클라이언트가 나중에 "outbox 에서" 완성된 객체를 본다.
                       자동 발행을 전제한다. 우리 정책은 자동 발행을 금지하므로
                       이 경로가 아예 없다
객체당 파일 하나       파트가 file 하나다. 이미지 4장 Note, Video + 자막(VTT),
                       렌디션 여러 개를 한 객체로 만들 수 없다
재참조가 없다          이미 올린 바이트를 다른 객체에 붙일 방법이 없다.
                       같은 파일을 다시 발행하려면 바이트를 다시 올린다
한계 탐색이 없다       최대 크기·허용 타입을 실패로 알아낸다
에러 모델이 없다       무엇을 거부했는지 말할 자리가 없다. 서버가 "껍데기를
                       완성" 하지만 무엇을 바꿨는지도 말하지 않는다
```

덧붙여 `202` 동안 그 `Location` 을 GET 하면 무엇이 오는지 정의되지 않았고, `Create` 래핑이
MAY 라서 클라이언트는 **저장됐는지 발행됐는지** 구별할 수 없다. 이것이 §14 가 가른 두
의미를 한 응답에 섞어 놓은 자리다.

## 2. 이미 FEP 가 채운 자리 — 재발명 금지

업로드 **메커니즘**을 제안하는 FEP 는 없다. 그러나 셋이 이미 그 주변을 정의했고, 하나는
제약을 건다.

| FEP | 우리가 쓰는 것 |
|---|---|
| **65ca** Common Client Configuration | 업로드 한계 탐색. `media` 객체가 이미 있다. 우리가 한계 탐색을 새로 정의하지 않는다 |
| **c180** Problem Details for ActivityPub | 에러 모델. applicability 에 "media upload" 가 **명시**돼 있다 |
| **ae97** Client-side activity signing | gateway endpoints 목록에 `uploadMedia` 가 들어 있다 — 존재를 전제한다 |
| **fe34** Origin-based security model | 제약. §9 을 보라 |

따라서 CG 초안의 결함 다섯 중 **둘(한계·에러)은 우리가 풀 문제가 아니다.** 남은 셋 —
완료 신호, 객체당 다중 파일, 재참조 — 이 설계의 몫이고 FEP 후보다.

## 3. 계약: CG 호환 단일 요청부터, 분리는 조건이 생길 때

처음 안은 바이트와 객체를 두 API 로 나누는 것이었다(JMAP core §6.1 모양). 재검토에서
**먼저 할 것이 아니라고 결론했다** — 나누면 미참조 blob 의 소유·만료·정리를 지금 정의해야
하고, 그 수명 계약은 첫 구현이 필요로 하지 않는다. §5 를 보라.

```txt
지금    1  업로드   POST .../uploadMedia   multipart: object 초안 + file  → 201 + Location(객체 URI)
        2  발행     POST .../outbox        Create(객체 URI)               → 201 + Location(Activity URI)
나중    0  바이트   POST {uploadUrl}       raw body                       → blobId
```

1 은 CG 초안의 요청 형식 그대로다. 제목·설명은 클라이언트 입력이고, `id`·파일 `url`·
렌디션·파일 속성은 서버가 확정한다.

**업로드는 어떤 경우에도 `Create` 를 기록하거나 배달하지 않는다.** MAY 를 쓰지 않는다.
발행 여부가 응답으로 모호해지는 것이 CG 초안의 결함이고, 우리에게는 2 가 있다. 업로드의
`Location` 은 객체 URI 이고 Outbox 의 `Location` 은 Activity URI 다.

### 두 레인 — 이것은 정책이고 스펙이 아니다

AS2 `attachment` 는 Object 도 Link 도 받으므로 로컬 Image 객체를 그 `id` 로 넣는 것은
합법이다. `axismundi-activities/docs/C2S.md` §13 이 거부하는 것은 **리모트 발행물**이고,
그 네 근거 중 로컬에서 살아남는 것은 하나뿐이다.

```txt
렌더링    inline 으로 {id,url,mediaType} 을 다 실으면 url 만 쓰는 구현도 그린다
삭제      양쪽을 우리가 가진다. 리모트 Delete 문제가 없다
저작자    같은 Actor 에 귀속된다. 남의 저작물이 우리 것처럼 보이는 문제가 없다
대화      **남는다.** Image 가 자기 replies · likes 를 가지면 상호작용이 두 곳으로 쪼개진다
```

그래서 금지가 아니라 **레인 분리**가 우리 정책이다.

```txt
미디어 라이브러리 레인   wp_posts attachment.  Note · Article 의 attachment 로 쓴다.
                        사이트 공유 자원이고 독립 AP 정체성이 없다(§13)
uploadMedia 레인         1급 미디어 객체.  영상 채널이 쓴다.  자기 id · url 을 갖고
                        그 자체로 발행 대상이다
```

**발행되지 않은 Image 객체 자체는 정당한 상태다.** Create 없는 로컬 객체는 §14 의
"만들었다" 경로에 이미 있는 상태이고, 업로드가 발행이 아니라는 정책의 직접적 결과다.
고아라서 치울 것이 아니다.

레인 분리의 결과로 **"이미지 4장 Note" 는 이 경로를 쓰지 않는다.** 그러므로 0 을 여는
조건은 "파일마다 객체가 생기는 비용" 이 아니다. 조건은 둘이다 — 한 객체가 파일 여러 개를
가져야 할 때(Video + 자막 · 렌디션), 또는 재개 가능 업로드가 필요할 때. 열 때는
상위집합으로 연다: `object` 파트의 AS2 가 **파트 이름**이나 blobId 를 참조하고(MIME `cid:`
의 역할) 서버가 그 자리를 채운다. CG 요청은 그 특수형으로 계속 받는다.

이 분리는 스펙이 요구하지 않는다. 우리 선호이므로 코드에 "스펙이 금지한다" 고 적지 말 것.

### 렌디션이 레인 분리의 두 번째 결과다

이미지 파생본은 **코어가 이미 만든다** — 미디어 라이브러리 attachment 의 서브사이즈이고,
그것을 광고하는 계약도 이미 구현돼 있다(`MEDIA-RENDITIONS.md`, FEP-1311, Implemented).
그 문서의 범위가 "Media Library attachment advertises its available media versions" 이고
"Projection does not generate images" 라고 적혀 있다.

그러므로 렌디션은 **attachment 레인에서 이미 풀려 있다.** uploadMedia 레인에는 코어 기계가
없다 — 우리 경로에 직접 쓰고 attachment 을 만들지 않으므로 서브사이즈가 생기지 않는다.
그 레인에서 렌디션이 필요한 것은 영상 트랜스코딩이고, 코어는 그것을 하지 않는다.

```txt
이미지   attachment 레인 · 코어 생성 · FEP-1311 로 광고        우리가 할 일이 없다
영상     uploadMedia 레인 · 트랜스코딩 · 코어에 없음            우리가 할 일이다
```

그래서 **첫 슬라이스는 영상에 집중한다.** 받는 타입을 영상으로 한정하면 "렌디션이 없는
미디어 객체" 가 설명되지 않는 상태가 아니라 트랜스코딩 이전의 정상 상태가 된다. 광고 규칙은
새로 만들지 않고 FEP-1311 을 그대로 쓴다 — **이미 존재하는 파생본만 광고한다.** 동기 처리
`201` 에서는 원본 하나뿐이고, 그것이 일관된다.

이미지도 이 레인으로 올릴 수 있게 되더라도 렌디션은 생기지 않는다. 그때 선택은 둘이다 —
렌디션 없이 원본만 광고하거나, 클라이언트가 만든 파생본을 받는 계약을 정하거나. 코어의
서브사이즈를 끌어오는 선택지는 없다. 그것은 attachment 을 만드는 일이고, 이 레인의 미디어를
attachment 수명주기에 묶는 일이다.

**타입 한정은 제품의 역할 분담이고 스펙의 제약이 아니다.** AS2 는 어떤 미디어 타입도
막지 않는다.

### 중복 제거와 재시도는 다른 문제다

같은 바이트로 제목이나 귀속이 다른 `Video` 를 두 개 만드는 것은 **정당하다.** 그러므로
파일 해시가 같다고 기존 객체의 `Location` 을 돌려주면 안 된다. 해시는 바이트를 공유하는
근거이고 객체를 식별하는 근거가 아니다.

응답 유실 재시도는 별도 키로 식별한다 — Actor 와 요청 주체에 묶인 업로드 키다. 선례가
이미 있다: outbox 의 `Idempotency-Key` 가 입력 해시와 묶여 저장되고, 같은 키에 다른 입력이면
`ax_c2s_retry_conflict` 로 409 다(`c2s-outbox.php`). 업로드도 같은 규칙을 쓴다.

```txt
같은 키 · 같은 입력      기존 객체의 Location 을 돌려준다
같은 키 · 다른 입력      409. 파일이 다르거나 객체 초안이 다르면 다른 제출이다
키 없음                  매 요청이 새 제출이다. 중복 객체는 클라이언트 책임
같은 바이트 · 키 없음    새 객체. 바이트만 공유한다
```

## 4. `blobId` 를 파일 URL 로 두지 않는다

제안은 자연스럽다 — 객체에 `url` 이 어차피 필요하고, 내용 주소 지정이면 같은 바이트가 같은
URL 이니 매핑 단계가 사라진다. 그런데 네 가지가 걸린다.

```txt
저장소가 둘이다      공개는 OP 경로, 비공개는 JMAP blob 저장소다. 비공개 저장소에는
                     URL 이 아예 없다(루트의 deny 가 트리 전체에 상속된다).
                     id 가 URL 이면 비공개 blob 은 id 를 가질 수 없다
호스트가 바뀔 수 있다 저장 목적지를 안 옮긴다는 약속은 **경로**에 대한 약속이고
                     호스트에 대한 약속이 아니다. §9 의 origin 분리를 나중에 택하면
                     URL 은 바뀌고, id 가 URL 이면 발급된 모든 id 가 바뀐다
가시성을 식별자에 박는다 URL 은 "이 주소에서 받을 수 있다" 는 주장이다. 비공개 초안
                     업로드를 지원할 수 없는 식별자가 된다
JMAP 과 충돌한다      RFC 8620 의 blobId 는 `downloadUrl` 템플릿의 **경로 조각**에
                     들어간다. 전체 URL 을 경로 조각에 넣으면 퍼센트 인코딩이
                     이중화된다. 불투명 문자열이라는 요구는 어기지 않지만
                     파싱을 유도한다
```

대신 **id 에서 URL 을 유도한다.** 원하는 성질은 전부 남고 비용만 빠진다.

```txt
blobId   'b' + SHA-256 hex          JMAP 저장소의 기존 규칙과 같은 대수
경로     {shard}/{hash}.{ext}       확장자는 content_type 에서 유도, 불명이면 거부
url      공개 저장소에서만 유도됨    비공개 저장소는 url 이 없다. 그것이 정상 상태다
```

클라이언트는 매핑하지 않는다 — 객체의 `url` 을 서버가 채워 돌려준다. 호스트를 나중에
옮겨도 id 는 산다.

**id 는 저장소 안에서만 의미가 있다.** 같은 바이트를 공개·비공개 양쪽에 올리면 두 저장소에
같은 digest 가 생기지만, 그것은 같은 blob 이 아니다. blobId 하나로 저장소를 가로질러
해소하지 않는다 — 승격 금지(목적지는 업로드 시점에 정한다)와 같은 규칙이다.

## 5. 미참조 수명 — 어느 설계에서도 정의해야 한다

A/B 분리의 비용은 **미참조 blob** 이다. 올렸지만 아무 객체도 참조하지 않는 바이트에
소유자·만료·정리를 정의해야 한다(JMAP 은 이것을 정의한다 — 미참조 blob 은 업로더만 읽고
만료된다. `axismundi-jmap/docs/BLOB-STORE.md`).

단일 요청에서는 그 상태가 생기지 않는다. 바이트는 항상 객체가 참조하고, 남는 것은
**발행되지 않은 객체**다 — 그리고 그것은 §3 이 적은 대로 정당한 상태다.

```txt
A/B 분리     미참조 blob        공개 저장소에서 처음 생기는 상태. 소유 · 만료 · 정리를
                               새로 정의해야 한다. JMAP 선례는 비공개 저장소의 것이다
CG 단일요청  미발행 객체        Create 없는 로컬 객체. 이미 정의된 상태다
```

그래서 첫 구현의 이점은 "정의할 것이 없다" 가 아니라 **"이미 정의한 것을 쓴다"** 다.

미발행 객체를 자동 삭제하지 않는다 — 발행하지 않은 미디어를 서버가 치우는 것은 사용자
데이터 삭제다. 관리 표면은 컴포저가 초안을 다룰 때 함께 정한다. A/B 를 열 때 비로소 미참조
blob 의 수명을 정의하며, 그때 **공개 저장소**의 규칙이 필요하다는 것이 분리의 실제 비용이다.

## 6. 완료 신호 — 미결

CG 초안은 outbox 를 완료 신호로 쓰고, 우리는 자동 발행을 하지 않으므로 그 신호가 없다.
그리고 AS2 에는 "처리 중" 어휘가 없다. 후보는 셋이다.

```txt
업로더 조회    객체는 즉시 존재하고 url 이 없다. 업로더에게만 읽히며 폴링한다.
               공개 가시성을 쓰지 않는다는 장점. 폴링이라는 단점
Notifications  우리 Notifications 가 수신 Actor 단위로 이미 있다.
               다른 구현에 이식할 수 없다는 단점
어휘           처리 상태를 표현하는 property. FEP 가 필요한 자리
```

**이번 구현에서는 동기 처리만 한다** — 처리할 것이 없으면 `201` 이고, `202` 를 쓰지 않는다.
`202` 는 비동기 처리를 실제로 구현할 때 완료 신호와 함께 들어온다. 쓰지 않는 상태 코드를
먼저 광고하면 클라이언트가 정의되지 않은 경로를 짜게 된다.

## 7. 선례: Emoji 가 이미 같은 문제를 풀었다

`axismundi-emoji` 에 **공개 바이트 저장소와 업로드 경로가 이미 있다**
(`uploads/axismundi-emoji/blobs`). attachment 을 만들지 않으면서 코어 검증을 통과하는
방법이 그 안에 있고, 이 설계는 그것을 다시 발명하지 않는다.

### 규칙은 "attachment 을 만들라" 가 아니라 "코어 검증을 우회하지 말라" 다

`local.php` 의 주석이 그대로 적고 있다 — *"The rule that matters is not 'must create an
attachment' but 'must not bypass WordPress's upload validation', so `wp_handle_upload()` is
mandatory and `move_uploaded_file()` is not an option — while the registry row, not an
attachment post, remains the record."*

그래서 §10 의 금지(⑧)와 충돌하지 않는다. 둘은 다른 층이다.

```txt
해야 할 것    wp_handle_upload() 로 받는다. 코어 검증을 통과한다
하지 말 것    attachment 행을 만들지 않는다. 기록은 우리 저장소의 행이다
수단          upload_dir 필터로 목적지를 돌린다
```

이것은 wp.org 심사 요구이기도 하다. `move_uploaded_file()` 로 직접 쓰는 업로드 경로는
검증 우회로 읽힌다.

### 두 진입점은 실재하는 구분이다

`wp_handle_upload()` 는 `is_uploaded_file()` 을 요구하므로 **진짜 POST 에만** 쓸 수 있다.
이미 디스크에 있는 파일 — 가져온 것, 가져다 넣은 것, CLI 가 건넨 것 — 은
`wp_handle_sideload()` 로 들어간다. 검증은 같다. 영상 레인에도 둘 다 필요하다.

### 두 함정이 주석에 남아 있다

```txt
필터 수명    업로드 호출 직전에 걸고 finally 에서 뗀다. 요청 끝까지 걸려 있으면
             같은 요청의 다른 플러그인 업로드까지 우리 저장소로 끌어온다 —
             두 플러그인이 한 요청에서 업로드할 때만 나타나는 버그다
필터 재귀    필터 안에서 경로 헬퍼를 부르지 않는다. 그 헬퍼가 wp_upload_dir() 를
             부르고, 그것이 이 필터를 다시 적용한다. 스택 오버플로가 PHP 를
             그냥 죽이므로 **에러가 아무 데도 안 남는다.** 코어가 막 건넨
             basedir · baseurl 로만 조립한다
```

### allowlist 는 코어에 더하는 것이지 대신하는 것이 아니다

Emoji 는 코어 검증 **위에** 자체 allowlist 를 얹는다. 근거가 적혀 있다 —
`get_allowed_mime_types()` 는 필터 가능하므로, SVG 를 켜는 플러그인(흔히 깔린다)이 깔리면
그 사이트가 결정한 적 없는 SVG 가 조용히 유효한 입력이 된다. 바이트를 직접 sniff 해서
자체 목록과 대조한다.

§9 의 보안 불변식이 이것을 요구한다. **코어의 허용 목록을 우리 allowlist 로 쓰면 안 된다** —
다른 플러그인이 넓힐 수 있는 목록이기 때문이다.

### 다른 점 하나 — URL 안정성

Emoji 의 저장 레이아웃은 `blobs/`(인스턴스별 디렉터리가 아니다)이고 업로드는
`blobs/incoming` 으로 들어온다. 영상은 `Video.url` 로 나가 리모트·엣지에 캐시되고 URL
불변이 요구사항이므로, **최종 경로가 내용 주소 지정이어야 한다**(`{shard}/{hash}.{ext}`).
그러므로 코어가 쓴 자리가 최종 자리가 아니다 — `incoming` 에서 받고 해시를 확정한 뒤
최종 경로로 옮긴다. Emoji 가 이미 같은 두 단계를 쓴다.

## 8. 저장과 삭제 계약

가져오는 것은 Emoji 의 코드가 아니라 **객체와 바이트의 수명이 다르다**는 원칙이다. 세
저장소가 같은 대수를 쓴다 — 내용 주소 지정, 확장자는 MIME 에서 유도, 실제 경로를 기록하고
재계산하지 않는다.

### 중복 제거

```txt
같은 바이트 · 다른 제목     Video 객체 URI 는 둘, 파일 URL 은 하나
같은 업로드의 재시도         Idempotency-Key 로 판단한다. 해시로 판단하지 않는다
```

해시는 바이트를 공유하는 근거이고 제출을 식별하는 근거가 아니다(§3).

### 파일 공개

검증과 해시 계산이 끝난 파일만 최종 경로에 **원자적으로** 공개한다 — staging 에 쓰고
`rename` 한다. 독자가 부분 파일을 보면 그것이 캐시되고, 내용 주소 지정 경로에서는 고칠
방법이 없다.

**계약은 "한 번 공개한 파일 URL 에 다른 바이트를 덮어쓰지 않는다" 다.** 저장소마다 다른
규칙이 아니다 — 외부에 노출되는 URL 이면 어디서나 같다(JMAP 쪽도 같은 문장을 적고 있다:
"바이트를 변경하거나 같은 경로를 덮어쓰는 API 는 없다").

`rename` 과 DB 기록은 한 트랜잭션이 아니다. 그러므로 **파일은 공개됐는데 객체 기록이
실패한 상태**가 생긴다. 내용 주소 지정이므로 이것은 오류 상태가 아니다 — 같은 바이트를
다시 올리면 해시가 같아 그 파일을 재사용한다. 보상 삭제를 하지 않는다.

### 삭제

```txt
Video 하나 삭제        공유 바이트를 지우지 않는다. 다른 객체가 그 해시를 주장한다
마지막 참조 소멸        첫 버전에서는 즉시 삭제하지 않는다
미발행 Video            파일을 참조하는 정상 객체다. 참조 계산에 포함된다
```

GC 는 업로드와 별개 작업이다. 참조 확인과 **동시 업로드 경합**을 검증한 뒤에 붙인다 —
마지막 참조를 지우는 순간 같은 해시가 새로 올라오는 경합이 이 설계의 실제 위험이고, 그것을
검증하지 않은 GC 는 발행된 URL 을 깨뜨린다.

Emoji 의 선례는 "아무도 그 해시를 주장하지 않을 때만 거둔다" 이고, 주석이 그것을
"reference-counted GC is scope-blind for exactly this case" 라고 적는다. 같은 규칙을 쓰되
구현 시점을 분리한다.

### 첫 감사

```txt
같은 파일로 Video 둘 생성   객체 URI 는 다르고 파일 URL 은 같다
하나를 삭제                 다른 객체의 파일이 여전히 조회된다
```

마지막 참조 회수는 GC 를 구현할 때 별도 감사로 둔다.

## 9. FEP-fe34 와 확장자 allowlist 의 격상

fe34 는 이렇게 말한다 — *"If the server allows clients to upload arbitrary files, it MUST
serve media from a different origin (e.g. from a different subdomain)."* 이유는 명시돼 있다.
공격자가 **AP 문서를 미디어로 업로드해** 검증을 우회하려 한다. 같은 줄에서 소비자 측 MUST
도 하나 더 걸린다 — GET 응답의 `Content-Type` 이 `activity+json` 계열인지 확인할 것.

우리 공개 경로는 사이트와 **같은 origin** 이다. 그러므로 fe34 의 MUST 를 피하는 것은 조건절
쪽이다 — 우리는 임의 파일을 받지 않는다. `content_type` 에서 확장자를 유도하고 알 수 없으면
거부한다는 기존 결정이 여기서 **보안 불변식으로 격상된다.**

```txt
불변식   정적 서버가 확장자로 Content-Type 을 고른다. 그러므로 allowlist 가
         activity+json · ld+json · json 으로 매핑되는 확장자를 절대 포함하지 않는다
첫 슬라이스  허용은 영상 타입뿐이다. 좁은 allowlist 는 이 불변식과 같은 방향이다
출처        코어의 허용 목록을 우리 allowlist 로 쓰지 않는다 — 다른 플러그인이
            넓힐 수 있다(§7). 바이트를 sniff 해서 자체 목록과 대조한다
의미     이 allowlist 는 편의가 아니다. 이것이 느슨해지면 fe34 의 조건절이 참이 되고
         우리는 미디어 서브도메인을 분리해야 한다
```

origin 분리는 열어 둔다 — 열어 두는 방법이 §4 의 "id 에서 url 을 유도한다" 다.

## 10. 지금 당장 할 것

```txt
① 라우트       POST axismundi/activitypub/actors/{uuid}/uploadMedia
               Actor 문서의 endpoints.uploadMedia 로 광고. 클라이언트는 조립하지 않는다
② 권한         UUID 를 권한 증명으로 쓰지 않는다. outbox 의 can_act_as() 를 재사용하고
               업로드 허용은 따로 검사한다(바이트 업로드는 발행이 아니다)
③ 수신         wp_handle_upload() (POST) · wp_handle_sideload() (디스크 파일).
               upload_dir 필터는 호출 직전에 걸고 finally 에서 뗀다. 필터 안에서 경로
               헬퍼를 부르지 않는다 — §7 의 두 함정
④ 저장         uploads/axismundi-object-projections/blobs/{shard}/{hash}.{ext}
               incoming 에서 받고 해시 확정 후 staging → rename 으로 공개한다.
               같은 해시가 이미 있으면 쓰지 않는다. 실제 상대 경로를 기록하고
               읽기·삭제는 기록된 경로만 쓴다(JMAP 선례). 계약은 §8
⑤ 객체         로컬 객체 저장소에 기록. id·url 은 서버가 채운다. Create 는 만들지 않는다
⑥ 재시도 키    Actor + 주체에 묶인 업로드 키. 같은 키·같은 입력이면 기존 Location,
               다른 입력이면 409. 해시만으로 기존 객체를 돌려주지 않는다
⑦ 응답         201 + Location(객체 URI). 거부는 c180 problem details
⑧ 금지         WP attachment 를 만들지 않는다. `wp_insert_attachment()` ·
               `wp_generate_attachment_metadata()` 가 편해 보이지만, 이 레인의 미디어를
               **attachment 수명주기에 묶는다** — 미디어 라이브러리 목록 · 코어의 삭제와
               재생성 · 서브사이즈 메타데이터가 그 행에 달려 온다. (경로가 강제되는 것은
               아니다. 저장 위치를 정하는 것은 `wp_handle_upload()` · `wp_upload_bits()`
               쪽이고 attachment 행 생성과는 별개다)
⑨ 삭제         Video 삭제가 공유 바이트를 지우지 않는다. 마지막 참조가 사라져도
               첫 버전은 파일을 남긴다 — GC 는 별개 작업이다(§8)
⑩ 감사         함수 호출이 아니라 **결과**를 본다 —
               업로드 후 WP attachment 행이 생기지 않는다 ·
               바이트가 OP 경로에 있다 ·
               `Location` 이 Video 객체 URI 다 ·
               원장에 `Create` 가 기록되지 않는다 ·
               allowlist 가 activity+json 으로 매핑되지 않는다 ·
               같은 바이트를 다른 제목으로 올리면 **객체가 둘**이고 바이트만 공유한다 ·
               같은 키 · 다른 입력이 409 다 ·
               같은 파일로 만든 Video 둘 중 하나를 지워도 다른 쪽 파일이 조회된다 ·
               Create 없이도 바이트는 공개다(이것이 정상 상태라는 것을 고정한다)
```

멀티파트 N 파일 변형은 ①~⑩ 다음이다. 컴포저는 WP 의 DataViews 업로드 예제에서 파일 선택·
진행·오류 UI 만 재사용하고, 전송은 이 계약으로 쓴다 — `wp.mediaUtils` 는 `/wp/v2/media` +
`sideload` 에 결합돼 있어 이 경로에 쓰지 않는다.

## 11. FEP 후보 경계

제안할 것은 **새 멀티파트 포맷이 아니라 의미의 예측 가능성**이다. CG 초안은 요청 형식을
정의하고 그 요청이 무엇을 확정하는지를 정의하지 않았다.

```txt
Location 이 가리키는 것      객체 URI 다. 파일 URL 도 Activity URI 도 아니다
자동 발행 여부               업로드는 Create 를 만들지 않는다. MAY 를 없앤다
202 이후 완료 확인           객체 URI 는 예약될 수 있다. 완료·실패는 별도 상태 표면
응답 유실 시 중복 방지        업로드 키. 해시는 중복 제거이지 재시도 식별이 아니다
```

제안하지 않을 것은 한계 탐색(65ca), 에러 표현(c180), origin 정책(fe34) 이다. 이미 있는
것을 다시 제안하면 세 FEP 와 경쟁하게 된다. 바이트/객체 분리와 다중 파일도 **먼저 구현해
보기 전에는 제안하지 않는다** — §3 이 그것을 조건부로 미뤘고, 겪지 않은 계약을 제안하는
것이 CG 초안이 한 일이다.

증거로 들 것은 수렴이다 — Mastodon 의 `POST /api/v2/media` 가 2단계이고(미디어 id 를 받아
status 에 붙인다), PeerTube 는 재개 가능 업로드를 쓴다. **구현들은 이미 CG 초안을 쓰지 않고
2단계로 갔다.** 이것은 측정해서 적을 것이고, 지금은 그렇게 기억한다고만 적는다.

착수 시기는 `activitystreams-open-items.md` 가 이미 정했다 — PeerTube 채널 Group 이식 때.
그보다 먼저 구현한다면 광고 시점을 분리한다: 라우트가 돌아도 Actor 문서에
`endpoints.uploadMedia` 를 넣지 않으면 아무 클라이언트도 쓰지 않는다.
